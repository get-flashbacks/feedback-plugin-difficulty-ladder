# Integration — feedBack-plugin-sectionmap

> For the shared multi-player contract used by Split Screen, `note_detect`,
> karaoke, and Section Map, see [`PLAYER_CONTEXT.md`](PLAYER_CONTEXT.md).
> This file keeps the Section Map-specific phrase/glass contract and formula.

> **Superseded (issue #63).** This file originally tracked issue #8, written
> against the Host-getters-only architecture `section_map` had at the time
> (see `COMPLIANCE.md` and the bottom "Original issue #8 record" section for
> that history). `section_map` was later rewritten to consume an event
> instead of independently reading `highway` getters, which silently made
> everything below the original section stale — it kept describing an
> architecture the code had moved on from. Issue #63's audit caught this
> plus a second, independent bug it enabled (see "Fill formula" below). This
> section describes the **current, real contract**; treat it as
> authoritative over anything below it.

## The actual contract

`difficulty_ladder` **is** the API `section_map` depends on: it emits a
`difficulty:sections-updated` event on `window.feedBack` (fired from
`calculateAndEmitSectionDifficulties()`, throttled at approximately 150 ms via
`scheduleSectionDifficultiesEmit()` — a trailing-edge throttle, not a debounce:
it fires periodically during a continuous change rather than only once at the
end; see `screen.js`), and
`section_map`'s current `screen.js` (`_smUpdateDifficultyFills` /
`_smGetSectionDifficulty`) does nothing but render whatever
`fillPercentage` / `glassSize` that event's payload carries per section. It
does **not** independently call `highway.getPhrases()` / `getMastery()` for
this — that code path doesn't exist in `section_map` anymore. (`section_map`
still reads `highway.getSections()` / `getSongInfo()` / `getTime()` directly
for the minimap's own layout, timing and seeking — none of that is part of
this contract.)

`difficulty_ladder`'s own player HUD (`drawHud()`) is a **separate**,
Host-getters-based consumer of the same `highway.getPhrases()` /
`getMastery()` data, for its own per-phrase glasses. It already knows to
defer to `section_map` when installed (`sectionMapOwnsGlasses` check —
`window.__slopsmithSectionMapHooksInstalled`), so in practice a user only
ever sees one glass renderer's output at a time. That mutual exclusion is
exactly why the fill-formula bug below went unnoticed for a while: the two
formulas' disagreement was never visible side by side, only as an
inconsistency in the *contract*.

**Availability check note:** `section_map`'s `_smIsDynamicDifficultyAvailable()`
also probes `window.feedBackViz_dynamic_difficulty` — a leftover from before
the `dynamic_difficulty` → `difficulty_ladder` rename that also assumed a
`type: "visualization"` viz-factory naming convention this plugin never
used. It's dead (this plugin has never set that global); the check works
today only because of the `window._ddCapabilities.sectionDifficulty` probe
alongside it. Worth deleting in `section_map` next time that file is
touched, not scope-creeped into this pass.

**Producer, not owner.** `difficulty_ladder` is *one possible producer* of
the underlying phrase data (`routes.py`'s `/generate` / `/generate-library`
routes), not its owner — `highway.getPhrases()` (which `calculateAndEmitSectionDifficulties()`
reads to build the event) returns whatever phrase ladder the song's
arrangement file has, whether generated by this plugin, hand-authored, or
shipped with the pack.

Everything below describes v2 (`difficulty:sections-updated`), the contract
Section Map consumes today. A render-neutral replacement,
`difficulty:sections-updated-v3`, is emitted alongside it — see
["sections v3"](#sections-v3--the-render-neutral-payload-issue-156) and its
["Transition policy"](#transition-policy).

## Fill formula (the issue #63 bug)

Before this fix, `drawHud()`'s per-phrase glasses and the per-section event
payload used **different formulas** for conceptually the same thing —
"how full is this glass at the current mastery":

- `drawHud()`: a **discrete tier** — `idxLevel = min(max_difficulty,
  floor(mastery * (max_difficulty + 1)))`, `fillFrac = idxLevel /
  max_difficulty` (or `1` when `max_difficulty === 0` — no tier ladder to
  climb).
- `calculateAndEmitSectionDifficulties()`: a **continuous** fraction —
  `mastery * maxSectionDifficulty / globalMaxDifficulty`.

These disagree materially for a lower-depth phrase/section: e.g. mastery
0.6 against a max_difficulty-2 phrase/section (of a song-wide max of 4)
lands on discrete tier 1 of 2 (50%), not the continuous formula's 30%.

**Fixed:** both now go through one shared helper, `_tierFillFrac(mastery,
maxDifficulty)` (`screen.js`), applied to the section's own aggregated
`maxSectionDifficulty` (the pre-existing max-of-overlapping-phrases rule is
unchanged) rather than scaled against the global max. `_presentedDifficultyLevel()`
(used by phrase-attempt logging) was refactored onto the same helper so
there is exactly one place this arithmetic is written. See
`tests/screen.test.js`'s `_tierFillFrac` and
`calculateAndEmitSectionDifficulties` tests.

**Tier scale (`top_difficulty`).** Generated ladders put every phrase on one
arrangement-wide tier scale: `max_difficulty` is the scale's top tier for
every phrase with a ladder, and a phrase that is complete early has sparse
level numbers (see README → "One difficulty scale per song"). So
`max_difficulty` no longer says how hard a phrase is. Core's
`getPhrases()` also reports `top_difficulty`, the tier from which the phrase
plays in full, and the glasses use that instead
(`_phraseTopDifficulty`, falling back to `max_difficulty` on an older core):

- glass height and `glassSize` scale with `top_difficulty`, and the payload's
  `maxDifficulty` / `avgDifficulty` are `top_difficulty` values;
- `_tierFillFrac(mastery, max_difficulty, top_difficulty)` picks the tier on
  the phrase's own scale exactly as before, then fills against the top:
  `fillFrac = min(1, idxLevel / top_difficulty)` — an easy phrase is full as
  soon as the slider reaches the tier it is complete at. With
  `top_difficulty === max_difficulty` (every fully authored ladder) this is
  the formula above, unchanged.
- A section's fill uses its hardest overlapping phrase (by `top_difficulty`).

## sections v3 — the render-neutral payload (issue #156)

The v2 payload above answers two questions a *glass* renderer needs: how full
is this section, and how big should the glass be. Both answers are presentation
decisions made here, in the producer, on Section Map's behalf — which is why
every consumer of `difficulty:sections-updated` inherits the glass metaphor
whether it wants one or not. v3 replaces those two fields with the facts they
were derived from, so a second renderer (a bar, a ring, a heat map, a
debug overlay) can be added without a third version of this contract.

v3 is **additive here**: both payloads are emitted, on separate event names,
from the same call (see "Transition policy" below).

| Emitted by | `calculateAndEmitSectionDifficulties()`, on the same ~150 ms throttle as v2 |
| Capability | `window._ddCapabilities.sectionsSchema === 'difficulty_ladder.sections.v3'` |

### Fields

Top level:

| Field | Meaning |
|---|---|
| `schema` | Always `difficulty_ladder.sections.v3`. |
| `player_context` | The full `player_context.v1` object for the pane this payload describes, or `null` for a legacy main-player emission while the Host is still resolving identity — identical to v2, per [`PLAYER_CONTEXT.md`](PLAYER_CONTEXT.md). |
| `mastery` | The pane's current mastery as a 0..1 number, or `null` when the highway reports nothing usable. |
| `max_tier` | Song-wide top of the tier ladder (`max_difficulty` over all phrases). 0 when no phrase has a ladder. Note this is the *ladder* top, not the same number as v2's `maxDifficulty`, which is a `top_difficulty` maximum kept for glass sizing. |
| `current_phrase_index` | Index into `highway.getPhrases()` of the phrase covering playback right now, else `null`. |
| `sections` | One entry per section that has at least one overlapping phrase, in `highway.getSections()` order. |

Each section entry, and each entry in its `phrases` array:

| Field | Sections | Phrases | Meaning |
|---|---|---|---|
| `id` | ✓ | ✓ | `section:<index>` for a section; for a phrase, the same `_phraseIdOf` string (`song::arrangement::index::start::end`) that `difficulty_ladder.phrase_attempt.v2` records are keyed by, so a consumer can join the two without a translation table. The `song::arrangement` prefix comes from the event's own `player_context`, not from the highway's song info — the two can disagree (a pane's `arrangement_id` vs the highway's `arrangement_index`) and only the context is what the attempt records were written with. Falls back to `phrase:<index>` when no song identity is available at all (no context and no usable song info). |
| `index` | ✓ | ✓ | Position in `getSections()` / `getPhrases()` respectively. |
| `start_time` / `end_time` | ✓ | ✓ | Half-open `[start_time, end_time)`, matching `drawHud()`'s and `tickScoring()`'s phrase cursor. `end_time` is `null` on a final, open-ended section (`Infinity` cannot be carried in a payload). |
| `is_current` | ✓ | ✓ | Whether this entry covers the current playback time. All `false` when the highway reports no time — an unreported time is not read as "at the start of the song". |
| `current_tier` | ✓ | ✓ | The tier this pane's mastery currently maps to, from the same discrete ladder every other consumer here uses (`_tierFillFrac`), clamped to `top_tier` — above that tier the entry is already played in full, so there is no larger tier to report. `null` when `mastery` is `null`. |
| `top_tier` | ✓ | ✓ | The tier from which this entry plays in full (`top_difficulty`, falling back to `max_difficulty` on an older core), clamped to `max_tier`. `0` means this entry reports *no ladder at all* (a single-level or hand-authored phrase), not "measured at the bottom tier" — the same reading v2 gives it, and the reason a 0/0 entry carries `current_tier: null` rather than a divided-by-zero result. |
| `max_tier` | ✓ | ✓ | The top of this entry's own tier ladder (`max_difficulty`). For a section: the largest `max_difficulty` among its overlapping phrases. `0` with `top_tier: 0` means "no ladder reported". |
| `avg_top_tier` | ✓ | — | Mean of the section's overlapping phrases' `top_tier`. This is v2's `avgDifficulty` only for a well-formed ladder: for a single-level section v2 averages its `max_difficulty` instead (its own fallback), so the two agree whenever the phrases report a ladder and can differ by one on a `top_tier: 0` section. |
| `has_chart_content` | ✓ | ✓ | Whether the span holds playable notes or chords. Probed per section over the full chart; a single-level phrase (`top_tier: 0`) inherits its section's verdict, because probing every phrase's own span would cost `O(phrases × notes)` and tell a renderer nothing it can act on. A phrase with a ladder is always reported as having content. |
| `phrases` | ✓ | — | The overlapping phrase entries, in `getPhrases()` order. |

### What it deliberately leaves out

- **No presentation field.** No `fillPercentage`, no `glassSize`, and nothing
  else that names a shape or a fraction of a shape — a renderer picks those.
  `current_tier` / `top_tier` / `max_tier` / `has_chart_content` carry every fact
  v2's percentage was derived from: `fillPercentage = 100 ×
  (has_chart_content ? min(1, current_tier / top_tier) : 0)` for a section that
  has a ladder, and `100` for one that doesn't (`top_tier: 0` with content — the
  easy-but-playable case). v2's own fallback for a missing entry is a 40 % floor,
  so rebuild that only if you want v2's exact glass rather than its inputs.
- **No entry for missing data.** A section with no overlapping phrase is
  absent from `sections` entirely, and a section whose phrases report no usable
  mastery gets `current_tier: null`. Absent/`null` means "nothing to show";
  it never degrades into a zero tier that reads as a real measurement.
- **No fabricated emptiness.** `has_chart_content` is what separates a silent
  section from an easy one — both report `top_tier: 0`, and v2 had to express
  that same distinction as 0% vs 100% fill (the PR #79 regression). It is
  computed from the full chart's own notes, exactly as v2 computes it, and
  only for entries where every overlapping phrase is single-level.

Aggregation is unchanged from v2, so the two payloads describe the same song:
a section's `top_tier` is the hardest overlapping phrase's, its
`current_tier` is drawn on that phrase's ladder, and a section is
`[sections[i].time, sections[i+1].time)`. The extra reads v3 adds are the ones
its new fields are *for* — the current time (for `is_current` /
`current_phrase_index`) and the song identity (for the joinable phrase `id`),
both plain getters on a value v2 already holds. There is no per-note or
per-phrase scanning beyond the content probe v2 already does, so v3 costs one
extra payload build per (throttled) emit.

### Transition policy

v3 ships **alongside** v2, not instead of it, and the two are separated three
ways so neither plugin's upgrade order can break the other:

1. **Separate event names.** v2 stays `difficulty:sections-updated`;
   v3 is `difficulty:sections-updated-v3`. A subscriber can never be handed
   the other version's payload and left to sniff `schema` — the payloads are
   not interchangeable, and neither is a subset of the other.
2. **v2 is frozen, not re-derived.** Its name, schema string and field
   semantics are unchanged, including the `fillPercentage` / `glassSize`
   values. An un-upgraded Section Map keeps working with no change at all,
   which is the whole point of emitting both from one call.
3. **The installed schema is advertised.** `window._ddCapabilities.sectionsSchema`
   says which contract the running `difficulty_ladder` speaks, so an upgraded
   Section Map picks v3 when it is there and stays on v2 when it isn't,
   instead of guessing from a payload. Read it when you subscribe rather than
   caching it forever — the global is set at this plugin's top-level script
   execution, which is why the load-order note below is load-bearing.

v2 (and `glassSize` with it) is removed in the follow-up that lands the v3
consumer in Section Map ([sectionmap#14](https://github.com/get-flashbacks/feedback-plugin-sectionmap/issues/14)),
once the released Section Map no longer depends on it. Nothing in this section
should be read as a promise that v2 is permanent.

## Fallback, timing, and stale-event behavior

- **Missing/delayed phrase data:** `calculateAndEmitSectionDifficulties()`
  bails (emits nothing) when `highway.getPhrases()` is falsy/empty, or a
  section has no overlapping phrase (that section is simply absent from
  `sectionDifficulties`, and from `sections` in the v3 payload).
  `section_map` renders "no glass" for any section
  index it never receives an entry for, and for a `fillPercentage` that
  isn't a number — same "no glass, not a misleading zero-fill glass"
  convention `drawHud()` follows when `hasPhraseData()` is false.
- **`section_map` not installed:** `difficulty_ladder` doesn't know or
  care — `fb.emit(...)` is a no-op if nothing's listening. `drawHud()`'s own
  Host-getters path keeps working independently.
- **`difficulty_ladder` not installed:** `section_map`'s
  `_smIsDynamicDifficultyAvailable()` returns false (no `_ddCapabilities`
  global was ever set), so it never subscribes to the event and never shows
  glasses — matches the "works standalone" requirement in `section_map`'s
  own `CLAUDE.md`.
- **Load-order / timing:** plugins load alphabetically, and `difficulty_ladder`
  < `section_map`, so `window._ddCapabilities.sectionDifficulty = true` (and
  `sectionsSchema`, for the v3 transition above) is set (at
  `difficulty_ladder`'s top-level script execution) before
  `section_map`'s `_smStartRealtimeHooks()` runs its one-time availability
  check. This ordering is load-bearing but undocumented in either repo
  before this pass — noted here and in `section_map`'s `CLAUDE.md`.
- **Stale events:** both section events are throttled but can still fire
  repeatedly over a song (mastery changes, phrase generation, song load).
  `section_map`
  applies whatever the *latest* event says, in place (`_smUpdateDifficultyFills`),
  without diffing against a previous value — a strictly-newer event always
  wins, so there's no meaningful "staleness" to detect (no timestamp/ordering
  guarantee is needed when the payload is just re-derived Host state, not an
  independent fact that can go out of sync with it).

### Acceptance-criteria checklist (as verified at the time, issue #8)

- [x] **Dynamic difficulty plugin exposes/forwards section-level difficulty values required by
      section map.** Confirmed this plugin does not need to forward anything — the values are
      already Host state both plugins read directly. Re-verified `screen.js`'s `drawHud()` and
      `tickScoring()` against the exact same three `highway` getters `section_map` now calls.
- [x] **Section difficulty values map correctly to visualization fill percentages.** Both plugins
      use the same formula: `idxLevel = min(max_difficulty, floor(mastery * (max_difficulty + 1)))`,
      `fillFrac = idxLevel / max_difficulty` (or `1` when `max_difficulty === 0` — nothing to fill
      toward). `section_map`'s `_smComputeGlass` implements this identically at the section level
      (aggregating over every phrase overlapping a section's time range via
      `_smSectionDifficulty`'s max-of-overlapping-phrases rule), verified by
      `feedBack-plugin-sectionmap/tests/screen.test.js`'s glass-fill tests.
- [x] **Verify behavior in both difficulty-maker and playback contexts.** No "difficulty maker"
      screen exists anywhere in the current feedBack codebase (checked `feedBack/plugins/` and
      `feedBack/static/` for any such screen) — see `COMPLIANCE.md`. Both plugins' difficulty
      visualizations only exist in the player context today. Documented as a scoping fact, not a
      gap either plugin can close unilaterally.
- [x] **Fallback behavior when section difficulty data is missing or delayed.** Both plugins
      degrade the same way: `hasPhraseData() === false`, or `getPhrases()` returning `null`/empty,
      or a section with no phrase overlapping its time range, all render "no glass" rather than an
      error or a misleading zero-fill glass. `section_map`'s `_smSectionDifficulty` returns `null`
      per-section for exactly this case (own tests: "marks a section null when it has no
      overlapping phrase, even if others do"); `difficulty_ladder`'s `drawHud()` hides its canvas
      entirely under the same condition.
- [x] **No regressions in dynamic-difficulty's existing flows.** This repo had no test harness
      before this pass. Added `tests/screen.test.js` (Node's built-in `node:test`, matching
      `feedBack-plugin-sectionmap`'s own convention) covering the pure helpers
      (`thresholds()`, `songKeyOf()`, `judgmentKey()`) untouched by this integration work, run
      before writing `screen.js`'s test-export branch and after — 7/7 passing both times. The only
      `screen.js` change made for testability was adding a Node-only `module.exports` branch at the
      very end of the file's IIFE (mirrors `section_map`'s own pattern); it's gated on
      `typeof module !== 'undefined'`, which is never true in a browser, so no runtime behavior
      changed for the actual Host.
- [x] **Documented with required configuration flags or version constraints.** None. Both plugins
      feature-detect every `highway` getter they call (`typeof highway.getPhrases === 'function'`
      etc.) rather than requiring a minimum Host version — consistent with best-practices rule 51
      ("degrade gracefully across Host versions").
