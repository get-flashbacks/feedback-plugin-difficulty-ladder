## The actual contract

`difficulty_ladder` **is** the API `section_map` depends on: it emits a
`difficulty:sections-updated` event on `window.feedBack` (fired from
`calculateAndEmitSectionDifficulties()`, debounced — see `screen.js`), and
`section_map`'s current `screen.js` (`_smUpdateDifficultyFills` /
`_smGetSectionDifficulty`) does nothing but render whatever
`fillPercentage` / `glassSize` that event's payload carries per section. It
does **not** independently call `highway.getPhrases()` / `getMastery()` for
this — that code path doesn't exist in `section_map` anymore. (`section_map`
still reads `highway.getSections()` / `getSongInfo()` / `getTime()` directly
for the minimap's own layout, timing and seeking — none of that is part of
this contract.)

`difficulty_ladder`'s own player HUD (`drawHud()`) is a **separate**,
Host-getters-based consumer of the same `highway.getPhrases()` /
`getMastery()` data, for its own per-phrase glasses. It already knows to
defer to `section_map` when installed (`sectionMapOwnsGlasses` check —
`window.__slopsmithSectionMapHooksInstalled`), so in practice a user only
ever sees one glass renderer's output at a time. That mutual exclusion is
exactly why the fill-formula bug below went unnoticed for a while: the two
formulas' disagreement was never visible side by side, only as an
inconsistency in the *contract*.

**Availability check note:** `section_map`'s `_smIsDynamicDifficultyAvailable()`
also probes `window.feedBackViz_dynamic_difficulty` — a leftover from before
the `dynamic_difficulty` → `difficulty_ladder` rename that also assumed a
`type: "visualization"` viz-factory naming convention this plugin never
used. It's dead (this plugin has never set that global); the check works
today only because of the `window._ddCapabilities.sectionDifficulty` probe
alongside it. Worth deleting in `section_map` next time that file is
touched, not scope-creeped into this pass.

**Producer, not owner.** `difficulty_ladder` is *one possible producer* of
the underlying phrase data (`routes.py`'s `/generate` / `/generate-library`
routes), not its owner — `highway.getPhrases()` (which `calculateAndEmitSectionDifficulties()`
reads to build the event) returns whatever phrase ladder the song's
arrangement file has, whether generated by this plugin, hand-authored, or
shipped with the pack.

## Fill formula (the issue #63 bug)

Before this fix, `drawHud()`'s per-phrase glasses and the per-section event
payload used **different formulas** for conceptually the same thing —
"how full is this glass at the current mastery":

- `drawHud()`: a **discrete tier** — `idxLevel = min(max_difficulty,
  floor(mastery * (max_difficulty + 1)))`, `fillFrac = idxLevel /
  max_difficulty` (or `1` when `max_difficulty === 0` — no tier ladder to
  climb).
- `calculateAndEmitSectionDifficulties()`: a **continuous** fraction —
  `mastery * maxSectionDifficulty / globalMaxDifficulty`.

These disagree materially for a lower-depth phrase/section: e.g. mastery
0.6 against a max_difficulty-2 phrase/section (of a song-wide max of 4)
lands on discrete tier 1 of 2 (50%), not the continuous formula's 30%.

**Fixed:** both now go through one shared helper, `_tierFillFrac(mastery,
maxDifficulty)` (`screen.js`), applied to the section's own aggregated
`maxSectionDifficulty` (the pre-existing max-of-overlapping-phrases rule is
unchanged) rather than scaled against the global max. `_presentedDifficultyLevel()`
(used by phrase-attempt logging) was refactored onto the same helper so
there is exactly one place this arithmetic is written. See
`tests/screen.test.js`'s `_tierFillFrac` and
`calculateAndEmitSectionDifficulties` tests.

## Fallback, timing, and stale-event behavior

- **Missing/delayed phrase data:** `calculateAndEmitSectionDifficulties()`
  bails (emits nothing) when `highway.getPhrases()` is falsy/empty, or a
  section has no overlapping phrase (that section is simply absent from
  `sectionDifficulties`). `section_map` renders "no glass" for any section
  index it never receives an entry for, and for a `fillPercentage` that
  isn't a number — same "no glass, not a misleading zero-fill glass"
  convention `drawHud()` follows when `hasPhraseData()` is false.
- **`section_map` not installed:** `difficulty_ladder` doesn't know or
  care — `fb.emit(...)` is a no-op if nothing's listening. `drawHud()`'s own
  Host-getters path keeps working independently.
- **`difficulty_ladder` not installed:** `section_map`'s
  `_smIsDynamicDifficultyAvailable()` returns false (no `_ddCapabilities`
  global was ever set), so it never subscribes to the event and never shows
  glasses — matches the "works standalone" requirement in `section_map`'s
  own `CLAUDE.md`.
- **Load-order / timing:** plugins load alphabetically, and `difficulty_ladder`
  < `section_map`, so `window._ddCapabilities.sectionDifficulty = true` is
  set (at `difficulty_ladder`'s top-level script execution) before
  `section_map`'s `_smStartRealtimeHooks()` runs its one-time availability
  check. This ordering is load-bearing but undocumented in either repo
  before this pass — noted here and in `section_map`'s `CLAUDE.md`.
- **Stale events:** the event is debounced but can still fire repeatedly
  over a song (mastery changes, phrase generation, song load). `section_map`
  applies whatever the *latest* event says, in place (`_smUpdateDifficultyFills`),
  without diffing against a previous value — a strictly-newer event always
  wins, so there's no meaningful "staleness" to detect (no timestamp/ordering
  guarantee is needed when the payload is just re-derived Host state, not an
  independent fact that can go out of sync with it).

## Original issue #8 record (superseded — kept for history)

Tracked issue #8, "Verify integration with feedBack-plugin-sectionmap section difficulty
visualization," done after `feedBack-plugin-sectionmap#1` (glass-filling difficulty viz) was
implemented against this plugin's data contract (see this repo's `COMPLIANCE.md` for how that
contract was established). At the time, `section_map` read `highway` getters directly
(`_smSectionDifficulty` / `_smComputeGlass`) rather than consuming an event — see "The actual
contract" above for what replaced this.

### Acceptance-criteria checklist (as verified at the time, issue #8)

- [x] **Dynamic difficulty plugin exposes/forwards section-level difficulty values required by
      section map.** Confirmed this plugin does not need to forward anything — the values are
      already Host state both plugins read directly. Re-verified `screen.js`'s `drawHud()` and
      `tickScoring()` against the exact same three `highway` getters `section_map` now calls.
- [x] **Section difficulty values map correctly to visualization fill percentages.** Both plugins
      use the same formula: `idxLevel = min(max_difficulty, floor(mastery * (max_difficulty + 1)))`,
      `fillFrac = idxLevel / max_difficulty` (or `1` when `max_difficulty === 0` — nothing to fill
      toward). `section_map`'s `_smComputeGlass` implements this identically at the section level
      (aggregating over every phrase overlapping a section's time range via
      `_smSectionDifficulty`'s max-of-overlapping-phrases rule), verified by
      `feedBack-plugin-sectionmap/tests/screen.test.js`'s glass-fill tests.
- [x] **Verify behavior in both difficulty-maker and playback contexts.** No "difficulty maker"
      screen exists anywhere in the current feedBack codebase (checked `feedBack/plugins/` and
      `feedBack/static/` for any such screen) — see `COMPLIANCE.md`. Both plugins' difficulty
      visualizations only exist in the player context today. Documented as a scoping fact, not a
      gap either plugin can close unilaterally.
- [x] **Fallback behavior when section difficulty data is missing or delayed.** Both plugins
      degrade the same way: `hasPhraseData() === false`, or `getPhrases()` returning `null`/empty,
      or a section with no phrase overlapping its time range, all render "no glass" rather than an
      error or a misleading zero-fill glass. `section_map`'s `_smSectionDifficulty` returns `null`
      per-section for exactly this case (own tests: "marks a section null when it has no
      overlapping phrase, even if others do"); `difficulty_ladder`'s `drawHud()` hides its canvas
      entirely under the same condition.
- [x] **No regressions in dynamic-difficulty's existing flows.** This repo had no test harness
      before this pass. Added `tests/screen.test.js` (Node's built-in `node:test`, matching
      `feedBack-plugin-sectionmap`'s own convention) covering the pure helpers
      (`thresholds()`, `songKeyOf()`, `judgmentKey()`) untouched by this integration work, run
      before writing `screen.js`'s test-export branch and after — 7/7 passing both times. The only
      `screen.js` change made for testability was adding a Node-only `module.exports` branch at the
      very end of the file's IIFE (mirrors `section_map`'s own pattern); it's gated on
      `typeof module !== 'undefined'`, which is never true in a browser, so no runtime behavior
      changed for the actual Host.
- [x] **Documented with required configuration flags or version constraints.** None. Both plugins
      feature-detect every `highway` getter they call (`typeof highway.getPhrases === 'function'`
      etc.) rather than requiring a minimum Host version — consistent with best-practices rule 51
      ("degrade gracefully across Host versions").

### Evidence (issue #8)
